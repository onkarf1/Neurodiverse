StriveTrack
Workflow and Architecture

A teacher-only workspace that checks whether a practice activity really lets a learner practice the skill in their approved IEP goal, rewrites it when it doesn't, protects every approved accommodation, and records practice sessions without ever scoring the learner.

AI suggests. StriveTrack verifies. The teacher decides.

1. Purpose, users, and the problem

The problem. Many IEP goals for autistic learners and learners with ADHD target executive-function skills: planning, sequencing, starting a task, holding steps in mind, checking one's own work, and adapting. Worksheets often quietly do that thinking for the learner. If a goal says "independently choose and explain a workable order" but the worksheet says "Follow these steps in order: 1… 2… 3…", the learner can finish it perfectly and never practice planning. Teachers rarely have time to catch this, and when activities are rewritten, approved accommodations (such as "Extra processing time") are easily lost.

Who uses it. Only teachers and case managers. Students never have accounts and never see the app directly; the teacher presents approved activities to the learner and records what happened.

PersonaNeedHow StriveTrack helps
Ms. Patel, special-education teacher, 14 studentsMake sure each practice activity matches each learner's goal without hours of re-reading.One-click alignment check with quoted evidence, a demand map, and an AI rewrite she approves.
Jordan, 16, autistic, goal: plan a work routineReal planning practice, with his approved supports every time.Unnumbered picture-cue cards, thinking-time timer, easier-reading mode, supports enforced in code.
Core promise. StriveTrack never decides mastery or progress. It records the teacher's decisions and the learner's chosen order and reasoning as evidence for the IEP team.

2. System architecture at a glance

Design principle. The browser holds no business rules that matter for safety. Every rule (accommodations present, approval required before practice, immutable decisions, verified quotes) is enforced in the backend, then mirrored in the UI only for convenience. The AI is an advisor whose output is checked by code before anyone sees it.

5. Runtime: how the system starts

  1. npm run setup creates backend/.venv with Python (override with STRIVETRACK_PYTHON, Python 3.13 used here), installs requirements.txt, and runs npm install in frontend/.
  2. npm run dev (scripts/dev.mjs):
    • Checks both ports first. If a port already serves StriveTrack it is reused; if it is occupied by something else, startup stops with a clear message. Existing services are never killed.
    • Starts python -m uvicorn app.main:app --host 127.0.0.1 --port 8001 in backend/ and Vite in frontend/.
    • Polls /api/health directly and through the Vite proxy for up to 10 seconds, then prints the URL. Ctrl+C stops only the servers it started.
  3. Backend startup: create_app() builds the Store (path from STRIVETRACK_DB or the default), builds the AIAssistant from .env (values in the shell win over the file), and in the FastAPI lifespan hook calls store.initialize(), which creates the tables and seeds the database the first time only.
  4. Browser: opens http://127.0.0.1:5173; all API calls go to relative /api/... and Vite forwards them to port 8001. CORS also allows ports 5173 and 4173 for direct calls.
The backend runs without auto-reload. After editing backend code or .env, restart npm run dev.

6.2 Seed data

9. Alignment check pipeline (POST /api/checks)

9.1 Exact steps

  1. Load and guard. Fetch the activity and its goal. If either is archived → 409 "Restore the archived activity and goal before running a check."
  2. AI review (only if a key is configured): ai.check(goal, content). Returns None on any failure. Details in §15.
  3. Acquire the lock and re-read the activity (it may have changed during the AI call).
  4. Rule: skill bypass. If the goal's skill mentions plan|sequenc|order|organis|organiz and the content either has a line starting 1. or 1) or contains one of "in this order", "in the correct order", "Follow these steps", "follow these steps", "already numbered", add a finding: type "Skill bypass", confidence 0.96, evidence = the first numbered line (or the phrase).
  5. Rule: support not stated. For each goal accommodation not found in the content (case- and spacing-insensitive), add "Support not stated", confidence 0.81, evidence = the first non-blank line of the activity.
  6. Verbatim filter. Keep only rule findings whose evidence is literally in the content.
  7. Unclear test. Content with fewer than 12 words, or with no task detail (numbered steps or "Step cards:"/"Task cards:") and fewer than 40 words, is unclear: rule findings are cleared.
  8. Merge AI findings only if the AI saw exactly the current content. Skip findings duplicating a rule finding (same type and evidence) and any whose type mentions "support" or "accommodation" (supports are the code's job). Add a note if the AI's quotes could not be verified ("1 AI suggestion was removed because…") or if the model didn't respond.
  9. Result. Any findings → mismatch. Else, unclear and (AI not used or AI also unsure) → unsure. Else → aligned.
  10. Summary. The AI's summary if the AI's own result matches the final result; otherwise a fixed rule summary.
  11. Demand map. The cleaned AI map if present; otherwise the rule map (planning and sequencing rows only: "done for learner" if steps are pre-ordered, "learner does" if there are cards or choice words, else "not required").
  12. Save the check with mode, ai_model, ai_note, and the goal and content fingerprints (§14). If the activity isn't approved, set it to needs_review. Write a "checked" history entry naming the model or "local rules".

9.2 Executive-function demand map

SkillMeaning
planningDeciding what needs to happen to reach the goal.
sequencingPutting steps in a workable order.
task_initiationStarting without being walked into it.
working_memoryHolding steps or information in mind.
self_monitoringChecking one's own work.
flexible_thinkingAdapting when something changes.

For each skill: does the goal target it (yes/no), and does the activity leave it to the learner (learner_does), do it for them (done_for_learner), or not need it (not_required)? A gap is a skill the goal targets that the learner does not do; the UI highlights gap rows in peach and counts them. Unknown skills and values from the AI are discarded.

10. Revision drafting pipeline (POST /api/revisions)

  1. Guard: archived goal or activity → 409.
  2. If the request has no content, call ai.revise(goal, activity) outside the lock. The model returns JSON {title, instructions, task_cards[3–5], reflection, rationale}. It must be grade-3 reading level, keep the same task and setting, start each card with an emoji picture cue, not number cards, not mention accommodations, and give a new title that doesn't give the plan away. Code validates 3–6 unique non-empty cards and non-empty instructions or returns None.
  3. Under the lock, re-read the goal and build Approved supports: followed by each accommodation word for word, added by code, never by the AI.
  4. Local template (fallback): take numbered lines from the original, or its existing "Step cards" section; otherwise three generic cards. Keep 3 and present them rotated [2nd, 3rd, 1st] so no correct order is shown. Text: title, "Your task: make your own plan for this routine…", step cards, supports, reflection questions.
  5. AI version: AI title, AI instructions, "Step cards:" with the AI's cards rotated by one (so they never appear in the order the model wrote them), supports, reflection.
  6. Version = highest existing version for the activity + 1. Accommodations default to the goal's list.
  7. Run the accommodation guard → draft or blocked. Save. History: "drafted", with the model name.

Editing a draft (PATCH /api/revisions/{id}) is allowed only for draft or blocked revisions. Each save re-runs the guard and writes an "edited draft" history entry stating whether supports are complete or which are missing. Deleting a draft writes "deleted draft".

11. The accommodation guard

Function missing_supports(goal, content, accommodations) returns every goal accommodation that is missing either from the revision text or from the revision's own accommodation list. Matching uses normalize(): whitespace collapsed to single spaces and Unicode case-folded, so "extra processing TIME" matches "Extra processing time".

  • Applied on create, on every save, and again at approval time.
  • Any missing support → status blocked, blocked_reason "Restore the approved accommodation(s): …". Approval returns 409 with that reason.
  • Applied again when opening a practice session. If the goal's supports changed after approval, practice is refused until a new revision is approved.
  • The UI shows a live checklist of supports (✓ or ⚠) while the teacher types, but the backend has the final say.

12. Approval, superseding, and the practice gate

Approve (POST /api/revisions/{id}/approve)

  1. Revision must be mutable (not approved, rejected or superseded) → otherwise 409.
  2. Goal and activity must not be archived.
  3. Guard re-run; blocked → 409.
  4. Revision → approved; activity → approved.
  5. Every older draft or blocked revision of the same activity → superseded with superseded_by = this version.
  6. History: "approved … All approved accommodations retained. Older draft v1 was retired so it cannot be approved by mistake."

Reject (POST /api/revisions/{id}/reject)

Requires a reason (3–1500 chars). Revision → rejected with rejection_reason; the reason is the history detail.

Practice gate (GET /api/try/{activityId})

Opens only if: the activity is approved; at least one approved revision exists (the highest version is used); the goal is not archived; and that revision still contains every current goal support. Then the backend extracts the step cards: text after a "Step cards:" / "Task cards:" marker, bullets and numbers stripped, stopping at supports or reflection lines, skipping lines that equal an accommodation, up to 6 cards. Fewer than 2 found → three generic steps.

13. Practice session record (POST /api/try/{id}/submit)

FieldRule

The session stores the revision id and version used and who recorded it. History: "session recorded … No mastery judgment was made." Sessions are listed under the practice screen (GET /api/sessions?activity_id=…).

Learner-facing aids on the practice screen

  • Larger cards and Easier reading (Verdana/Tahoma font, letter spacing 0.12em, word spacing 0.16em, line height 1.8, following WCAG 1.4.12). Both are remembered in localStorage.
  • Read cards aloud: browser speech synthesis with a local English voice at rate 0.85; if none exists, the teacher is told to use the device's tools.
  • Thinking time: 1, 2 or 3-minute visual countdown bar with pause, resume and reset. If the goal has a time-related support (matches "time", "pause" or "wait"), starting the timer ticks that support as used. Screen readers hear a message only when time is up.
  • Card order is changed with up/down buttons (keyboard accessible); each move is announced to screen readers.

14. Out-of-date check detection

When a check is saved, two short fingerprints are stored:

goal_fingerprint    = sha256(normalize(skill + "\n" + criteria + "\n" + sorted accommodations))[:16]
content_fingerprint = sha256(normalize(activity content))[:16]

Each time checks are read (GET /api/checks, GET /api/checks/{id}), the backend recomputes both from the current goal and activity. If either differs, it adds stale: true and stale_reasons: ["goal", "activity"]. The Check screen then shows a yellow notice: "This check is out of date: the goal and activity changed after it ran. Run the check again before you rely on it." Changes to a title, due date or colour do not make a check stale; only meaning-bearing text does. Checks without fingerprints (created before this feature, until a reset) are treated as current.

15.2 The call

_chat(system, user) posts {model, temperature: 0.2, messages:[system, user]} to /chat/completions with a Bearer key and a 60-second timeout. Any HTTP error, timeout, or malformed response returns None. _parse_json() removes <think>…</think> reasoning blocks and ```json fences, then parses the outermost {…}.

15.3 Check prompt (summary)

Explains executive-function "bypasses" (pre-ordered steps, choice already made, answers or completed example given, working-memory overload), says accommodations are handled separately, requires a word-for-word evidence quote, forbids diagnosing or judging the learner, caps findings at 4, allows "unsure", and asks for the six-skill demand map in fixed JSON.

15.4 Verification of AI output

  • Quotes: locate_quote() builds a regex of the quote's words joined by \s+, case-insensitive, needing at least 2 words. If found, the exact passage from the activity replaces the AI's text; if not, the finding is dropped and counted.
  • Confidence for AI findings is fixed at 0.7 (rules: 0.96 and 0.81); the type is capped at 60 chars and the explanation at 600.
  • Demand map: only the six known skills and three known values survive; goal_targets must be literally true.
  • Revision: 3–6 unique cards, non-empty instructions; title whitespace-collapsed and ≤80 chars (falls back to the activity title).
Boundary: the AI never sees learner codes, sessions, observations, or user names, and never writes accommodations, approves anything, or changes status. It only proposes text, and code decides what is kept.

16. Backend internals

16.1 Store and concurrency

  • Store.connect() opens a fresh SQLite connection per operation with timeout=15 and PRAGMA busy_timeout=15000, committing on success.
  • Methods: initialize, reset, all(entity), get(entity, id) (404 "Goal not found." etc.), put, delete.
  • A process-wide re-entrant lock (threading.RLock) wraps every read-modify-write sequence (updates, approvals, checks), so two requests can't interleave. AI calls happen before taking the lock.
  • Filtering, search and sorting happen in Python in paginated(): case-insensitive text search across title, content, skill, criteria, note, context, actor, action, target and detail; filters for status, category, goal_id and activity_id; sort by updated_at, title, created_at or due_date; page size 1–100 (default 12).

16.2 Authentication (simulated)

Login checks the email (case-insensitive) and the shared demo password and returns token = "demo-" + user.id. Every protected endpoint uses current_user(), which requires Authorization: Bearer demo-… and loads the user (401 otherwise). Public: /api/health, /api/demo-users, /api/auth/login. The frontend stores the token under strivetrack-token; any 401 fires a strivetrack:unauthorized event that signs the teacher out and clears the query cache.

Tokens are not signed, so this is not real security. That is acceptable for a local MVP with synthetic data; school single sign-on is on the roadmap.

16.4 Relationship protection

  • Deleting a goal with linked activities → 409 (archive instead).
  • Deleting an activity that has an approved or rejected revision → 409. Otherwise its revisions, checks and observations are deleted with it.
  • Changing an activity's goal after revisions exist → 409.
  • Creating an activity as "approved", or PATCHing it to approved → 409.

17.2 Data layer

  • api<T>(path, init) adds the JSON header and Bearer token, turns non-OK responses into ApiError(message, status), and prefers per-field validation messages.
  • Query keys, for example: ['activity-options'], ['activity', id], ['goal', id], ['checks', id], ['revisions', id], ['ai-status'] (cached 60 s), ['try', id], ['sessions', id], ['observations', id], [kind, {q, status, sort, page}].
  • After each mutation (check, draft, save, approve, reject, delete), affected queries are invalidated so every panel refreshes from the backend. Archiving in the library is optimistic and rolls back on error.
  • Dates are shown in the America/Phoenix time zone.

17.3 Check workspace in detail

  • Progress bar: step 1 → step 2 once the activity has a check → step 3 once it's approved; completed steps show a tick, and the current step has aria-current="step".
  • AI status note: "AI-assisted (qwen3-30b-a3b) · quotes verified · supports enforced in code · no learner data sent", or "Local rules", with a neutral loading state.
  • Side-by-side goal card (skill, success criteria, supports) and original activity card with an "Edit this activity" deep link.
  • Check result: result badge and summary, AI note, out-of-date notice, demand map table, finding cards with quoted evidence and a source chip ("AI · quote verified" or "Local rule"), mode and date footer.
  • Revision editor: version picker, AI rationale banner, textarea (read-only for final states), save button, blocked reason; the approval card shows the live support checklist, Approve (disabled while there are unsaved changes, missing supports or a blocked status), Reject, Delete, or "Run a practice session".
  • Teacher observations panel below.

22. Privacy, safety, and responsible AI

RiskControl in StriveTrack
AI invents evidenceEvery quote is located in the activity; unverifiable findings are removed and the teacher is told how many.
AI drops an accommodationThe AI never writes supports; code inserts them verbatim, and approval is blocked if any is missing.
AI shows the "right" orderCards are unnumbered and rotated by code before display.
Over-trust in AIEvery AI output is labelled with the model name; findings show their source; the teacher must approve; approval is a confirmation dialog.
AI unavailableLocal rules always run; a note says the model didn't respond.
Student privacyTeacher-only app; learner codes not names; only goal and activity text is sent to the model; sessions and notes stay local; synthetic data.
Labelling learnersPrompts forbid diagnosing or judging; the app never scores mastery.
Relying on stale resultsFingerprint-based out-of-date flag (§14).
AccountabilityAppend-only history of every decision, edit and session.
SecretsKey lives only in git-ignored .env on the server; never sent to the browser.
